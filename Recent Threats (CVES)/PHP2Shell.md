## 1. الأول: إيه هي `session.upload_progress`؟

تخيّل إنك بترفع ملف حجمه 100 MB على موقع، والمتصفح بيعرضلك:

- Uploading: 25%
    
- Uploading: 60%
    
- Uploading: 90%
    

علشان الموقع يعرف عملية الرفع وصلت لفين، PHP عنده Feature اسمها `session.upload_progress`.

الـ feature دي بتسجّل معلومات عن عملية رفع الملف، زي:

- اسم الملف أو عملية الرفع.
    
- حجم البيانات المتوقع.
    
- عدد الـ bytes اللي وصلت لحد اللحظة دي.
    

وبتخزّن المعلومات دي في `$_SESSION`، بحيث Request تاني يقدر يقراها ويعرض نسبة التقدم للمستخدم.

يعني باختصار:

Browser

بيرفع ملف للسيرفر

PHP Upload Parser

بيقرأ بيانات الملف وبيتابع التقدم

`$_SESSION`

بيحتفظ بمعلومات الـ upload progress

دي في الأصل Feature مفيدة، ومش ثغرة لوحدها.



<img width="1086" height="310" alt="image" src="https://github.com/user-attachments/assets/f9771315-2e86-43c5-95f7-935d4350be47" />


## 2. إيه علاقة `multipart/form-data` بالموضوع؟

لما تبعت Form فيه File، المتصفح غالبًا بيستخدم Content-Type اسمه:

`multipart/form-data`

وده بيسمح للـ Request إنه يحتوي على أكتر من جزء، مثلًا:

- Field فيه اسم المستخدم.
    
- Field فيه بيانات إضافية.
    
- Field فيه الملف نفسه.
    

الـ PHP Upload Parser بيقرأ الأجزاء دي أثناء معالجة الـ Request.

فيه إعداد اسمه:

`session.upload_progress.name`

والقيمة الافتراضية بتاعته:

`PHP_SESSION_UPLOAD_PROGRESS`

لما الـ Request يحتوي على Field بالاسم ده، PHP يقدر يبدأ يسجّل معلومات التقدم الخاصة بعملية الرفع.

خد بالك: الاسم ده مش اسم الملف، لكنه اسم الـ Form Field اللي بيشغّل آلية تسجيل الـ progress.

## 3. أهم نقطة: التوقيت! ⏱️

هنا بقى مربط الفرس 

فيه فرق بين مرحلتين:

المرحلة الأولى: Request Body Parsing

PHP بيقرأ الـ Request Body، ويعالج بيانات الـ multipart upload، ويحدّث بيانات الـ upload progress.

قبل تشغيل كود التطبيق

المرحلة الثانية: تنفيذ التطبيق

PHP يهيّئ بيئة الـ Request، وبعدها ينفّذ سكريبت الـ PHP المطلوب.

بعد معالجة الـ Body

يعني لو عندنا صفحة اسمها `index.php`، فالسكريبت مش لازم يكون بدأ التنفيذ علشان PHP يكتب بيانات الـ upload progress في الـ Session.

وده معناه إن جزءًا من المعالجة بيحصل قبل ما التطبيق نفسه يبدأ شغله.

## 4. طيب إيه الخطورة في كده؟



عادةً ممكن تتخيّل إنك علشان تتعامل مع Session في صفحة معينة، لازم الصفحة تعمل:

```
<?php
session_start();
```

لكن الـ `session.upload_progress` بيشتغل في مرحلة سابقة على تنفيذ كود الصفحة.

بالتالي، وفقًا لشرح الروم، المهاجم مش محتاج إن السكريبت المستهدف يستدعي `session_start()` بنفسه علشان آلية الـ progress تبدأ.

وكمان مش شرط يحتاج Login لمجرد الوصول لمرحلة معالجة الـ Upload؛ ده يعتمد على إمكانية الوصول للـ endpoint وإعدادات السيرفر.

لاحظ الفرق:

|الاعتقاد|الحقيقة|
|---|---|
|لازم الصفحة تنفّذ كود علشان يحصل أي تأثير|بعض معالجة الـ Request بتحصل قبل كود الصفحة|
|لازم الصفحة تستدعي `session_start()` علشان تبدأ آلية الـ progress|الآلية ممكن تبدأ قبل تنفيذ السكريبت|
|لازم الـ endpoint يحتوي على منطق رفع ملفات معقّد|وفقًا للروم، استقبال POST قابل لمعالجة الـ multipart قد يكون كافيًا للوصول للمرحلة دي|

لكن: ده لا يعني إن أي POST Request على أي سيرفر هيؤدي لثغرة أو لـ RCE. لازم باقي شروط الاستغلال تكون موجودة.

## 5. إيه المقصود بـ Pre-execution window؟

تخيّل إن عندك شركة:

- البوابة الأمامية بتستقبل الطرود.
    
- الموظفين المسؤولين عن محتوى الطرود لسه ما بدأوش شغلهم.
    
- فيه نظام آلي بيسجّل معلومات عن كل طرد بمجرد وصوله.
    

لو المشكلة موجودة في النظام الآلي نفسه، فممكن يحصل التأثير قبل ما الموظف المسؤول عن التطبيق يشوف الطرد أصلًا.

ده تقريبًا المقصود بـ Pre-execution window: الفترة اللي PHP فيها بيعمل معالجة للـ Request قبل تشغيل كود التطبيق.

في PHP2Shell، دي نقطة البداية اللي هنحتاج نفهمها علشان نعرف إزاي الـ vulnerability بتتطور من مجرد معالجة Upload إلى التأثير اللي الروم بتدرسه.

## 1. الأول: يعني إيه Memory وPointer؟

تخيّل إن الـ RAM عبارة عن عمارة فيها شقق، وكل شقة ليها رقم.

البرنامج بيحجز شقة علشان يخزّن فيها بيانات، وبيكون عنده عنوان الشقة علشان يعرف يرجعلها.

Pointer = عنوان الشقة

## 0x1000

العنوان ده بيشاور على

Memory Block

البيانات اللي البرنامج مخزّنها

إذن:

- Memory: المكان اللي فيه البيانات.
    
- Pointer: متغير بيحتفظ بعنوان المكان ده.
    

لحد هنا تمام؟ تعالى نشوف المشكلة.

## 2. إيه اللي بيحصل لما البرنامج يحرر الـ Memory؟

لما البرنامج يخلص من البيانات، بيعمل عملية اسمها `free()`، يعني بيحرر المكان علشان الذاكرة دي تبقى متاحة لإعادة الاستخدام.

تخيّل إنك سبت الشقة ومشيت، والشقة بقت متاحة لشخص تاني.

المشكلة إنك لو لسه محتفظ بعنوان الشقة القديم، فالعنوان موجود، لكن مش معناه إن الشقة لسه ملكك أو إن البيانات القديمة لسه موجودة.

وده بالضبط أساس فكرة الـ Dangling Pointer.



<img width="1013" height="322" alt="image" src="https://github.com/user-attachments/assets/ddd0228e-89f9-4048-ad74-aea1dd8875b7" />


## 3. طيب إيه علاقة نفاد الـ Memory بالموضوع؟

تخيّل إن PHP عندها خطوات لازم تعملها بالترتيب:

1. تحرر الـ Memory القديمة.
    
2. تحدّث الـ Pointer علشان ما يفضلش بيشاور على المكان القديم.
    
3. تكمل شغلها بصورة طبيعية.
    

لكن لو الذاكرة خلصت في اللحظة الحرجة بين الخطوة الأولى والتانية، PHP ممكن تعمل حاجة اسمها Bailout.

الـ Bailout هنا زي إن حد ضغط زر الطوارئ، فالبرنامج خرج فجأة من مسار التنفيذ قبل ما يكمّل كل عمليات التنظيف.

النتيجة المحتملة:

- الذاكرة اتحررت.
    
- الـ Pointer لسه محتفظ بالعنوان القديم.
    
- الـ Request انتهى، لكن حالة الـ Pointer داخل العملية ما اتصلحتش.
    

ودي هي المشكلة الأساسية اللي الروم بتشرحها.

دي أهم حتة 

في إعداد Apache `prefork` مع `mod_php`، ممكن نفس الـ Worker Process يخدم أكتر من Request واحد بالتتابع.

خد بالك: مش معنى كده إن أي Request تاني هيعمل اختراق. لازم يوصل لنفس الـ Worker، وتتحقق ظروف إضافية للاستغلال.

## 5. من هنا ظهر نوعان من الهجوم

الروم بتشرح إن الباحثين قدروا يبنوا هجومين مختلفين من أصل المشكلة نفسها:

Memory Disclosure

بدل ما البرنامج يقرأ البيانات اللي المفروض يقرأها، ممكن يقرأ بيانات غير متوقعة من الذاكرة ويكشفها للمهاجم.

زي إنك تفتح شقة بعنوان قديم وتلاقي فيها بيانات تخص شخص تاني.

Remote Code Execution (RCE)

في الهجوم التاني، استغلال فساد الحالة ممكن يوصل للتأثير في مسار تنفيذ البرنامج، وبالتالي تنفيذ كود على السيرفر إذا اكتملت شروط الاستغلال.

والـ ASLR اللي الروم هتتكلم عنه بعد كده هو حماية بتحاول تخفي أماكن أجزاء مهمة في الذاكرة. تسريب عناوين فعلية ممكن يساعد في تجاوز جزء من الحماية دي.

## 6. ليه الروم ظبطت السيرفر بإعدادات خاصة؟

الروم بتذكر إعدادات بتسهّل إعادة إنتاج المشكلة:

- Prefork + mod_php: نفس الـ Worker Process ممكن يعالج Requests متتابعة.
    
- Single worker: يقلل احتمالية إن الطلب التالي يروح لعملية مختلفة.
    
- Low `memory_limit`: يخلي الوصول لحالة نفاد الذاكرة أسهل.
    
- `session.upload_progress` enabled: يوفّر مسار معالجة الـ Upload اللي شرحناه قبل كده.
    

الفكرة إن إعدادات اللاب بتقلّل العوامل المتغيرة، علشان تقدر تلاحظ الـ Bug بصورة أوضح.

أما في بيئة إنتاج حقيقية، تعدد الـ Workers وارتفاع حدود الذاكرة ممكن يصعّب توقيت الاستغلال، لكنه مش دليل وحده على إن الثغرة مستحيلة.
